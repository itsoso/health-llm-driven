# Agent 写入失败恢复设计

> 实施状态：代码与 G3/G4 闸门已完成；等待提交、生产部署和 G5/G6 验证。

## 问题

健康写入回合失败后，助手可能询问用户是否重试；用户回复“需要”时，
新回合只看到这两个字，无法恢复原始饮食文本、图片和写入目标。继续让模型
从自然语言历史猜测写入参数，会造成漏写、错写或重复写。

## 决策

在现有 Agent Runtime 和消息持久化之上增加一个内容最小化的恢复绑定：

- 失败助手消息只保存 `source_message_id`，不把健康正文或工具参数复制到
  Runtime 控制面。
- 仅当原回合是健康写入、没有已验证回执、没有 in-flight/uncertain/verified
  写入检查点，且终态明确可重试时，才生成恢复动作。
- 用户紧邻回复“重试/需要/好”等窄集合短语时，服务端按用户、会话和消息顺序
  回取原始用户消息；不允许跨会话、跨用户或跳过中间消息。
- 原消息的文本和图片只用于本轮执行。界面仍保存用户真实回复“需要”，不会
  伪造一条重复的用户消息。
- 新回合使用自己的写入检查点和幂等身份；图片来源仍绑定原消息，以便记录卡
  复用原图。
- 如果原回合存在不确定写入，禁止自动重试，继续由 Runtime reconcile 路径处理。

## 不变量

1. 一个恢复确认最多触发一次新 Run。
2. 原写入可能已发生时，不允许重放。
3. 恢复成功最多产生一个业务记录和一个已验证回执。
4. 失败恢复绑定不保存健康正文。
5. 图片只能从当前用户拥有的持久化消息读取。

## 非目标

- 不迁移 Agent 框架。
- 不在 `agent_runs` 或工具账本保存健康正文。
- 不把任意“好/继续”解释为重试；没有紧邻、有效恢复动作时保持普通对话。
