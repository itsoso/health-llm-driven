# 健康记录纠正原子性修复设计

## 背景

2026-08-08 的生产验收发现：用户先记录饮水 300ml，随后说“改成 350ml”。系统创建了记录 #718，但纠正回合连续生成了格式错误的 `health_manage.update` 参数，之后把更新错误降级成“删除旧记录后重新创建”。删除成功，重新创建被写入意图守卫阻止，导致旧记录丢失；最终回复还把删除回执显示为笼统的“已写入”。

这不是单纯文案问题，而是更新操作失去原子性、意图与实际动作不一致，以及回执动作语义缺失的组合故障。

## 目标

- “修改已有记录”只允许查询目标和原地更新，不得自动退化为删除后重建。
- `health_manage.update.data` 若为可解析且结果为对象的 JSON 字符串，在工具边界规范化为对象；其他非法值明确拒绝且不产生副作用。
- 写入回执和客户端提示区分新增、更新、删除，不把删除展示成“已写入”。
- 保持用户主动、明确的独立删除能力不变。
- 修复后恢复本次被错误删除的生产饮水记录为当天 350ml，并用真实设备验证新增→修改→删除闭环。

## 方案选择

采用分层安全修复：参数规范化 + 意图/操作一致性守卫 + 动作感知回执。

未采用的方案：

- 只修参数解析：虽然能降低本次模型失败概率，但仍允许更新意图被错误执行成删除。
- 新增完全确定性的通用“修改上一条记录”执行器：长期价值较高，但改动面超出 1.3.3 发布阻断修复。

## 设计

### 1. 工具参数规范化

在统一工具校验边界处理 `health_manage.update.data`：

- 已是对象：保持不变。
- 是字符串且可解析为 JSON 对象：转换为对象后继续现有校验。
- 字符串解析成数组、标量，或无法解析：返回现有可恢复校验错误。
- 空对象：继续按现有规则拒绝。

规范化只修复表示形式，不猜测字段、不补写数值、不扩大写入范围。

### 2. 意图与操作一致性守卫

Agent Kernel 已把本轮识别为 `mutate/.../update` 时：

- 允许 `health_manage.list` 查询候选记录。
- 允许 `health_manage.update` 修改已锁定目标。
- 阻止 `health_manage.delete`，返回稳定的策略错误，不触达业务 API。
- 继续阻止使用 `health_record.create` 代替更新，除非用户在新的回合明确要求新增。

守卫位于业务派发前，因此即使模型反复重试或改变计划，旧记录也不会被删除。

### 3. 动作感知回执

健康记录回执增加经过白名单约束的动作语义，并由客户端/通用文案映射为：

- create → 已写入/已新增
- update → 已更新
- delete → 已删除

动作字段只来自已校验的工具参数，不信任模型自由文本；现有 `resource_type`、`resource_id` 和 `verified` 仍是成功事实真源。

### 4. 失败处理与数据恢复

- 参数校验失败：明确告诉用户未修改，原记录保持不变。
- 意图/操作不一致：明确阻止，不产生删除回执。
- 更新已取得可验证回执：清除同一目标的旧参数错误，最终回复以成功结果为准。
- 更新未取得回执或结果不确定：不宣称成功，进入既有核验/重试流程。
- 生产修复部署且验证通过后，按用户已确认的 350ml 目标恢复当天记录；恢复前后查询并记录非敏感证据，不输出审核账号凭据。

## 测试与验收

测试先行覆盖：

1. `data` 为合法 JSON 对象字符串时可原地更新。
2. `data` 非法、为数组或标量时拒绝，且没有业务派发。
3. 更新意图下的删除调用被阻止，业务删除端点未执行。
4. 用户明确删除时仍可删除。
5. 同一目标先参数失败、后更新成功时，最终状态为成功且不残留旧错误。
6. create/update/delete 回执展示动作准确。
7. 生产真机完成饮水新增、修改、删除；数据库读回与界面一致。
