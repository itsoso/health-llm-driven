## 核心调整：常规发布只核对当前版本与一个回滚版本

将“发布审计证据”和“备份内容”分开管理。常规发布的制品检查集合限定为：当前生产版本、本次候选和一个明确指定且已验证的回滚版本。旧备份进入归档，不再逐个读取文件或遍历其依赖目录。

| 对象 | 常规发布 | 何时完整读取内容 |
| --- | --- | --- |
| 本次候选制品 | 核验 SHA、摘要、构建回执与适用运行时 | 构建完成、安装前以及内容发生变化时 |
| 当前生产与一个回滚版本 | 核验绑定关系、健康与必要完整性 | 发布切换、指定回滚版本变化、实际回滚时 |
| 已归档历史备份 | 校验已封存索引与相关增量证据，不扫描备份目录 | 恢复、重新晋升为回滚候选、独立归档巡检时 |
| 旧授权、消费记录、失败操作和审计回执 | 保留撤销、防重放、未完成操作阻断检查 | 证据封存及有新增记录时；不得因归档备份而跳过 |

实施方式：

1. 首次迁移执行一次完整历史校验，生成版本化、受完整性保护的封存索引，绑定原操作终态、原始回执摘要、制品摘要和已覆盖范围，同时保留原撤销检查。签名/校验密钥的用途与权限在实现设计中明确，不把普通可写 JSON 当作可信凭证。
2. 后续轮换检查封存索引、全部小审计/撤销证据、封存后的新增操作及当前回滚集合；不遍历已封存 archived 备份内部。新增未知操作、未完成 claim、失效签名或撤销异常继续阻断。
3. 封存证明的是“这些历史证据在封存时已经验证”，不声称归档文件此刻仍完整。任何归档恢复必须重新读取完整内容，与原始摘要对比，通过后才能成为可用回滚版本。
4. 候选成功安装且健康验证通过后，原当前版本成为唯一回滚版本；再旧的备份退出发布检查集合。引用、恢复操作或发布锁未释放时不能回收制品。
5. 不通过删除历史锁、消费记录或原始审计回执获得性能收益。归档实体的删除是独立保留策略，必须确认不被引用且已有可用回滚版本；本规划不执行删除。
6. 索引更新采用原子写入并绑定发布锁。现有 `rotate/install/revoke/recover` 及 Web/OTA 各入口统一采用同一规则，不能只加速 rotate 后在其他入口重新扫描全部历史。

当前候选已同步 `docs/governance/deploy.md`、服务器/独立 bootstrap 和测试。首次 seal 仍全量核验历史，日常 archived 只跳过其备份正文与内部遍历，小审计/顶层库存仍全部核验。无索引或未启用新版的线上工具继续旧全量检查，不能仅删掉旧循环。

## 当前候选已实现的范围

- **权限测试修复**：固定夹具的初始模式，确保真正发生权限变化；保留真实不安全权限拒绝测试，不删除旧断言。是否恢复发布准入仍由新候选的精确 CI 裁决。
- **历史封存与活动回滚集合**：`trusted_release_server.py` 使用私有 HMAC checkpoint、代次链与 anchor，绑定当前 live publication 和其回滚备份。首次 seal 完整读取全部历史；日常仅对已封存且审计一致的 archived 备份省略 blob 哈希和内部遍历，仍读取全部小审计、日志摘要、原回执与顶层库存。新完成操作经过校验后才更新代次，未知/未完成操作继续阻断。此实现针对前端 publication 历史，不宣称所有其他历史数据已统一归档。
- **独立 seal/inspect/finish**：canonical bootstrap 的 `seal-frontend-history --sha` 不依赖轮换成功才能首次封存；`--inspect` 只读检查原部分 checkpoint，`--checkpoint-sha256` 只完成该原更新。完整 CI、来源、原锁、授权策略、无活动租约/进程及 OTA 历史闭合仍须通过；seal/finish 还核验 live 内容和活动回滚集合。部分更新保持 BLOCK，不生成新授权、不重置 claim、不自动重跑。
- **Runner transport**：`trusted-release.yml` 的精确 source/CI gate 后、生产凭据前增加固定 `39.98.206.178:22` 五秒只读 TCP/SSH 标识检查。`target=transport` 仅 preflight，不认证、不读凭据、不 claim。成功不证明鉴权或主机身份；真实发布仍须 SSH host key、只读 readiness、执行前 CI 复证与一次性 claim。没有实际 runner 回执不能宣布网络阻断解除。
- **分段性能证据**：历史检查记录阶段、耗时、实际核验与归档数量、可用 I/O 差值；缺失计数不当作零。`deploy.sh` 保留本地/远程独立时钟及原失败语义，新增 Pi 安装 started/completed。Pi 安装仍执行，未因 Python 锁缓存跳过。排队、vendor 构建及全链路统一性能基线尚未齐备。

HMAC 保护 root 私密状态下的内容和绑定变化，不提供独立外部防回滚。密钥与全部 state 同时被 root 回退不在威胁覆盖内。封存只证明封存时的历史验证；旧备份恢复或晋升为回滚前必须重新全量读取并对照原摘要。

既有同主机制品准备/原子消费、锁文件未变时依赖复用、源码协商及并行安装保持有效；本轮不把已有能力重新算作新增收益。Pi 缓存、跨 runner 工具镜像和更广的制品复用尚未实现，需先测量收益、绑定和失效条件，再决定 P2/P3 后续范围。详见 [授权校验 I/O](../ops/release-authorization-io.md)。

## 结构性验收与回退

- 用同一当前/回滚集合，增加多组大体积归档备份：常规发布对归档文件的内容读取次数为零，且不遍历归档内部文件；只读封存索引、全部小审计及必要新增证据。
- 修改当前或回滚制品、撤销记录、候选绑定、索引签名，或加入未完成操作，必须阻断。
- 归档备份损坏：记录不可恢复状态，不能选作回滚；若与当前发布无引用关系，不将其重新加入每次发布的内容检查。
- 归档恢复时摘要不符必须拒绝；索引原子写入失败、进程中断、锁竞争、新增未知证据均不能伪装封存成功。
- 先在隔离库存比较新旧判定，再进行一次真实库存迁移；生产启用必须使用干净、受审且精确 CI 绿色的 revision。
- 性能目标是消除历史制品正文读取、避免重复打包、提前发现不可发布状态。墙钟 p50/p95 目标待新基线确定；不承诺“八分钟必然减半”。
- 索引无法验证时保持阻断，由显式恢复流程回到旧的完整检查路径；不删除回执、不重置已消费操作、不自动降级放行。
