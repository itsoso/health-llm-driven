# 构建与发布关键路径优化规划

日期：2026-10-10。状态：规划，尚未实施下述结构性调整。

用户目标：常规发布不再核对大量历史备份；减少构建、授权和部署中的重复工作。优先减少实际工作量，再考虑并发。

## 现状与证据

- 本次生产元数据清点发现四组历史 Web 备份，合计 2,727,305,688 字节、210,290 个目录项。旧流程两次完整内容读取，仅此部分约 5.45 GB。原进程八分钟采样的 `read_bytes=8016338944` 还包含其他 I/O，不能全部归因于这四组备份。
- `bd93515a03e3aab8f2989d792974f08ba6236e7c` 已实现单次轮换内的摘要复用，但第一遍仍检查全部历史，第二遍仍遍历全部目录。这是过渡优化，不能解决随历史增长的开销。
- 该 SHA 的 [CI 38015061345](https://github.com/itsoso/health-llm-driven/actions/runs/38015061345) 失败：`test_memo_never_hides_changed_history[unsafe-mode]` 没有抛错。该测试把文件改成 `0600`，夹具没有固定初始模式，且替换了真实权限检查；当原模式已经是 `0600` 时没有形成模式变更。应固定测试前置状态，并另用真实检查器证明不安全权限被拒绝，不能删除断言或放宽发布闸。
- 当前另有 GitHub runner 到生产 SSH 的连通性阻断；增加本地校验不能解决它。新工具尚未用于生产授权轮换，没有新的部署或 OTA 成功回执。
- 数据库发布备份已经默认跳过，见 `docs/specs/2026-09-14-release-backup-cadence.md`；不重复提出这一优化。
- `deploy.sh` 已有阶段计时和锁文件未变时的依赖复用；可信 workflow 的 backend 与 ios-build 已可并行，TestFlight 上传依赖 ios-build。后续只优化实测重复项。

## 核心调整：常规发布只核对当前版本与一个回滚版本

将“发布审计证据”和“备份内容”分开管理。常规发布的制品检查集合限定为：当前生产版本、本次候选和一个明确指定且已验证的回滚版本。旧备份进入归档，不再逐个读取文件或遍历其依赖目录。

| 对象 | 常规发布 | 何时完整读取内容 |
| --- | --- | --- |
| 本次候选制品 | 核验 SHA、摘要、构建回执与适用运行时 | 构建完成、安装前以及内容发生变化时 |
| 当前生产与一个回滚版本 | 核验绑定关系、健康与必要完整性 | 发布切换、指定回滚版本变化、实际回滚时 |
| 已归档历史备份 | 校验已封存索引与相关增量证据，不扫描备份目录 | 恢复、重新晋升为回滚候选、独立归档巡检时 |
| 旧授权、消费记录、失败操作和审计回执 | 保留撤销、防重放、未完成操作阻断检查 | 证据封存及有新增记录时；不得因归档备份而跳过 |

实施方式：

1. 首次迁移执行一次完整历史校验，生成版本化、受完整性保护的封存索引，绑定原操作终态、原始回执摘要、制品摘要、撤销状态和已覆盖范围。签名/校验密钥的用途与权限在实现设计中明确，不把普通可写 JSON 当作可信凭证。
2. 后续轮换只检查封存索引、封存后的新增操作及当前回滚集合。新增未知操作、未完成 claim、失效签名或撤销异常继续阻断。
3. 封存证明的是“这些历史证据在封存时已经验证”，不声称归档文件此刻仍完整。任何归档恢复必须重新读取完整内容，与原始摘要对比，通过后才能成为可用回滚版本。
4. 候选成功安装且健康验证通过后，原当前版本成为唯一回滚版本；再旧的备份退出发布检查集合。引用、恢复操作或发布锁未释放时不能回收制品。
5. 不通过删除历史锁、消费记录或原始审计回执获得性能收益。归档实体的删除是独立保留策略，必须确认不被引用且已有可用回滚版本；本规划不执行删除。
6. 索引更新采用原子写入并绑定发布锁。现有 `rotate/install/revoke/recover` 及 Web/OTA 各入口统一采用同一规则，不能只加速 rotate 后在其他入口重新扫描全部历史。

此调整需要同步 `docs/governance/deploy.md` 的历史校验合同、服务器实现和测试。现行合同要求的全量检查在新版合同及实现通过验证前继续执行，不能仅在旧函数里删掉循环。

## 其他优化及实施顺序

| 顺序 | 工作 | 收益与边界 | 验收 |
| --- | --- | --- | --- |
| P0 | 修复上述跨平台权限测试，恢复精确 SHA CI | 先消除现有失败；不弱化权限校验 | Linux/macOS 确实形成模式变更；真实不安全权限用例拒绝；完整 release CI 通过 |
| P0 | 将只读网络、runner、候选与 CI readiness 检查前置 | 发现 SSH 阻断后立即停止，避免先做昂贵轮换 | 连通失败时未写退休 intent、未消费授权；执行变更前仍再次校验 |
| P0 | 扩展现有阶段计时为统一性能回执 | 分开记录排队、源码准备、授权、构建、环境、依赖、迁移、健康、OTA；记录内容读取字节与扫描项数 | 同一候选、同一工作集；冷/暖缓存分组交替运行，保存原始结果，不以缓存效应冒充并发收益 |
| P1 | 实施封存索引与一个回滚版本集合 | 常规发布开销与历史备份内容总量脱钩 | 见下方结构性验收；首次迁移耗时单独报告 |
| P2 | 按组件变化确定构建范围 | 纯 mobile OTA 不重复 Web/native 构建；后端是否需要部署由精确 SHA 合同与变更范围决定 | 未知范围保守全量；DB/契约变化保留 PostgreSQL 与两侧类型验证；后端 SHA Gate 保留 |
| P2 | 同一候选制品构建一次，后续阶段验证并使用 | 减少 validate、publish 或上传阶段再次打包 | 制品绑定源码、依赖锁、构建配置、环境与 mobile runtime；缺失/不匹配重新构建或阻断，不采用不可信共享缓存 |
| P2 | 分析并合并重复环境检查 | 环境文件及校验器均未变时，可复用一次候选绑定的昂贵解析结果，执行前保留便宜的身份和摘要复核 | 内容/权限/工具变化立即失效；敏感值不进入日志或缓存；先测量现有路径 |
| P3 | 优化源码与工具准备 | 核查每个可信 job 重复下载/安装耗时，评估只读制品或锁定工具环境 | 每个 job 仍独立验证 canonical 来源、owner、精确 SHA、清洁状态；凭证阶段不执行不可信缓存代码 |
| P3 | 按实测调整 CI 分片与排队 | 当前已有 timing-balanced matrix；优先最长分片、安装重复与 runner 排队 | 保持测试全集覆盖、必需 job 名与真实成功状态，不靠跳过安全/集成测试缩短时间 |

网络检查失败不自动重发已消费的发布或 OTA。现有一次性 claim、失败回执与恢复合同保持有效。

## 结构性验收与回退

- 用同一当前/回滚集合，增加多组大体积归档备份：常规发布对归档文件的内容读取次数为零，且不遍历归档内部文件；只读封存索引及新增审计证据。
- 修改当前或回滚制品、撤销记录、候选绑定、索引签名，或加入未完成操作，必须阻断。
- 归档备份损坏：记录不可恢复状态，不能选作回滚；若与当前发布无引用关系，不将其重新加入每次发布的内容检查。
- 归档恢复时摘要不符必须拒绝；索引原子写入失败、进程中断、锁竞争、新增未知证据均不能伪装封存成功。
- 先在隔离库存比较新旧判定，再进行一次真实库存迁移；生产启用必须使用干净、受审且精确 CI 绿色的 revision。
- 性能目标是消除历史制品正文读取、避免重复打包、提前发现不可发布状态。墙钟 p50/p95 目标待新基线确定；不承诺“八分钟必然减半”。
- 索引无法验证时保持阻断，由显式恢复流程回到旧的完整检查路径；不删除回执、不重置已消费操作、不自动降级放行。
