当天 15:01（Asia/Taipei）的跑后分析与恢复通知，线上通知记录的 Telegram
渠道成功，iOS APNs 渠道均返回 `APNs not configured`。汇总 `sent` 仅表示至少
一个渠道成功，不能作为手机收到推送的证据。

实际服务用户为 `health-app`，配置中的 APNs 私钥存在，但目录为
`root:root 0700`，文件为 `root:root 0600`。服务身份无法遍历目录，导致
`IOSPushService.is_configured` 的文件存在检查失败。

经独立安全审查后，仅调整配置所指密钥的目录和文件：保留 root 所有权，
组设为专用 `health-app`，目录权限 `0750`、文件权限 `0640`。操作前确认
无符号链接或额外 ACL、父目录由 root 控制且服务不可写、目录仅有目标密钥、
目标组仅包含服务账户。未复制密钥、修改密钥内容、修改 env 或发送通知。
操作审计保留在服务器 journal 的 `reva-apns-permission` tag。

后续在已恢复运行的后端及 Celery worker 的 mount namespace 中，以实际
服务身份和进程环境分别验证：`configured=true`、`jwt_generated=true`。
验证不输出私钥或 JWT。这证明配置及签名能力恢复；未证明 APNs 接受了新消息，
也未证明手机显示。期间观察到另一发布切换服务，本任务未干预其发布或重启。
