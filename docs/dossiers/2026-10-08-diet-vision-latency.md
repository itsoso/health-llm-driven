## 基线与实现

生产识别模型只读核验为 `qwen-vl-max`。沿用同一 provider、图片、温度 0.1、
输出上限 2000、原始全部识别规则与字段，在 system prompt 末尾追加：

> 输出格式：JSON 用单行紧凑格式，不加缩进或字段之间的空白；保留全部要求的字段与规则。

base64 和 URL 两条入口使用同一构造函数。原 prompt 1736 字符，候选 1781 字符。
本轮不是输入压缩；实际 API 输入增加 28 tokens，收益来自生成空白与排版减少。
模型、未知值处理、食品清洗、数据库校准、用户绑定、确认条件、幂等和写入回执均未调整。
回退方式是取消这一个格式后缀，两条入口共同恢复原 prompt。

## 真实 API 对照

只读重放同一用户近期三张成功图片，以及四张无个人数据的合成图片：
营养标签、含推荐未购项的食品订单、药品/补剂与图片指令注入、健康应用界面。
原图与识别正文仅在权限受限的本机/服务器临时目录，仓库只保留固定样本编号和聚合元数据。
逐次保留现有第三方 AI 同意校验，未执行饮食写入，未修改生产设置。
脚本是受信操作者的独立 CLI，不是任意多用户重放服务；指定同意用户不证明任意文件的所有权。

初筛 9 次调用发现 Flash 在一个真实样本返回零食物，拒绝切换模型。
[初筛元数据](../reviews/2026-10-08-diet-vision-screening.json)保留失败。

首次扩大对照有一个样本同时包含餐食与食品订单标签，oracle 误限定
`source`/`nutrition_basis=vision_estimate`，导致两侧共同失败。
保留[原失败报告](../reviews/2026-10-08-diet-vision-initial-oracle.json)，
仅移除这两个不适用的类别断言，保留食品身份、空克数、字段和禁止声称已写入等检查。
整个七样本矩阵重新调用，未给旧结果重新评分或删掉失败。

[正式对照](../reviews/2026-10-08-diet-vision-output-final.json)：七样本，每侧两次，
按样本和重复次数交替先后顺序，顺序调用。28 次全部 API 成功、合同失败为零。
营养标签数值和基准、订单食品数量与未知规格、非食物拒识别、JSON 字段与禁止写入声明通过。
