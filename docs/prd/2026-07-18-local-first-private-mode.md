# 小巴本地优先私有模式 PRD

> Status: implemented; native validation
> Updated: 2026-07-19
> Canonical product: `docs/prd/reva-personal-health-os-prd.md`
> Feature spec: `docs/specs/active/2026-07-18-local-first-private-mode.md`

## 1. 决策

把 Mobile 从“登录后访问服务端 Health OS 的客户端”扩展为“可独立运行的本地 Health OS 节点”。用户下载后无需注册即可记录、查询、计算和导出个人健康数据；注册只用于可选的端到端加密同步、换机恢复和跨设备协同。

第一条端到端切片是完全离线的饮食记录：文字、手工、常吃食物、条码/OCR 和受能力约束的端侧模型都只生成待确认草稿，确认后写入设备内加密存储；营养计算来自可追溯的本地食物数据库，不来自模型记忆。

## 2. 用户问题

当前 Mobile 未认证时只能停留在登录页。HealthKit、饮食、Agenda、Health Twin、Safety Guardian 和长期因果账本均以服务端 PostgreSQL 为真源。即使用户只想做最基本的私人记录，也必须先建立服务端身份并把健康数据发送到云端。

这带来三个问题：

- 首次使用门槛与“下载即用”冲突；
- 高隐私用户无法选择真正不出设备的路径；
- 断网或服务不可用时，Mobile 的长期核心价值无法独立成立。

## 3. 目标用户与核心价值

首批仍服务 Reva 的既定锚点用户，但增加一个明确需求：愿意持续记录饮食和健康行为，同时不愿在验证价值前注册或上传原始健康数据。

核心承诺：

> 无需注册、无需联网，健康信息只属于用户；需要同步或更强推理时，再由用户逐项开启。

## 4. 核心循环映射

```text
本地输入
  -> 本地候选草稿
  -> 确定性清洗与营养表校准
  -> 用户确认 WriteIntent
  -> 本地 DietRecord + ExecutionEvent
  -> 本地日汇总 / Health Twin 投影
  -> 下一次更快的常吃食物匹配
```

这加强 `Capture -> WriteIntent -> ExecutionEvent -> HealthTwin -> Review`，不把产品降格为孤立的卡路里工具。

## 5. 产品原则

1. 本地模式是一等产品，不是受限试玩版。
2. 本地数据默认不出设备；任何云端推理必须逐次说明发送内容。
3. 注册提供恢复和同步价值，不成为记录功能的准入门槛。
4. 小模型只生成候选，不直接写健康事实。
5. 营养数字来自本地可追溯数据与确定性计算。
6. 照片份量无法可靠确认时显示未知或区间，不能伪装成测量值。
7. “完全本地”以飞行模式验收，不以隐私文案验收。
8. Sentry、遥测、推送和远程配置都必须服从严格本地模式的网络断路器。
9. 本地保险库只在设备已设置系统锁屏密码时创建；不以弱保护模式静默降级。
10. 每次导出由 App 生成新的高熵恢复密钥，不接受用户自设弱密码作为第一版恢复根密钥。

## 6. 模式定义

| 模式 | 数据真源 | 推理 | 同步 |
|---|---|---|---|
| 严格本地 | 设备 | 仅端侧能力 | 无 |
| 本地优先 | 设备 | 默认端侧；逐次授权云增强 | 可选密文同步 |
| 云端账户 | 服务端兼容路径 | 服务端编排 | 现有同步 |

现有账户用户不自动迁移。第一阶段保持云端路径不变，新用户可选择“立即开始”创建本地身份；若设备没有系统锁屏密码，App 解释原因并引导设置后重试，不创建弱保护保险库。

## 7. 第一切片：完全本地饮食

### 7.1 必须有

- 无需注册进入 App；
- 本地身份和本地数据删除；
- 手工与文字饮食记录；
- 常吃食物和最近记录；
- 本地食物库匹配与营养计算；
- 草稿确认后写入；
- 当日合计；
- 加密导出与恢复；
- 首次持久化前明确提示“恢复需要导出文件 + 独立恢复密钥”，但允许用户稍后备份；
- 飞行模式完整可用；
- 端侧能力可用性和降级说明。

### 7.2 端侧智能

- 确定性中文解析器：从常见口语提取食物、数量、单位和餐次，保证旧设备离线可用；
- Chinese-CLIP RN50 int8：随 App 打包，只返回最多三个图片身份候选；
- 图片候选必须由用户选择后再生成独立草稿，不估份量、不算营养、不自动保存；
- 用户历史：同一常吃餐的纠正结果优先于再次推理。

### 7.3 不做

- 不承诺从单张照片精确称重；
- 不让模型直接产生正式营养事实；
- 不在第一期迁移完整 Health Twin、用药、化验、基因或跨端 Safety Guardian；
- 不为本地用户静默创建影子云账户；
- 不把第三方食物数据库打包前的授权问题当成实现细节略过。

## 8. 成功指标

- 新用户无需注册完成首餐记录的比例；
- 飞行模式首餐完成率；
- 草稿确认率与纠正率；
- 从打开记录入口到获得正式回执的时延；
- 本地记录连续使用天数；
- 云端增强主动开启率，而不是强制登录转化率；
- 严格本地模式网络请求数必须为零。

## 9. 风险

- Apple 系统模型只覆盖支持并开启 Apple Intelligence 的设备；
- 系统模型随 OS 更新而变化，必须版本化评测；
- 通用端侧视觉模型对混合中餐和份量判断可能没有产品价值；
- 食物数据库的覆盖、来源和授权可能比模型更难；
- 本地真源与现有服务端真源并存会增加仓储与同步复杂度；
- 未备份用户卸载 App 后可能永久丢失数据；
- 用户移除设备锁屏密码会使设备专属密钥不可用，恢复必须同时持有此前导出的文件和对应恢复密钥；
- 端到端加密同步意味着现有服务端无法直接计算用户 Health Twin。

## 10. 发布策略

内部 capability spike 已证明目标真机不能依赖 Apple 系统模型，并完成 Chinese-CLIP 探索推理。第一阶段通过可见模式配置开放严格本地、本地优先和云端账号三种路径；因包含本地数据库与原生模型桥，必须走新 iOS 包，不能只走 OTA。任何扩大到其他健康域的工作必须基于饮食切片的真实纠正率、离线完成率和数据恢复证据重新过 Gate。
