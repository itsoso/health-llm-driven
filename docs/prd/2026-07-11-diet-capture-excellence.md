# 饮食打卡极致体验 PRD

## 目标

把 Mobile 饮食 Capture 做成可信、快速、可纠错、可分享的日常闭环：用户拍照后立即看到进度，识别结果按食物和份量展开，明确克数优先使用 reviewed food table，确认后只写一次，随后可以生成适配微信和小红书的高级感图片卡。

## 成功标准

- 数据：确认成功必须返回真实 `diet_record_id`；重复确认或网络重试不得重复写。
- 准确：UI/OCR 文案不得进入 food_items；明确 g/kg/克/斤份量命中 reviewed table 时以表值为营养真源；无法确定份量时明确显示“估算”。
- 性能：相机返回后 100ms 内进入可见处理态；12MP 照片先在端侧压到最长边 1568px、JPEG q0.7，再生成 Base64，避免原图占用 JS 内存和网络。生产分别采集端侧准备耗时、压缩后 payload、成功 recognition p50/p95、confirm p50/p95、无正文纠错率，并单列失败/取消；目标为 recognition p50 <= 6s、p95 <= 15s，confirm p95 <= 1.5s。
- 交互：每个识别食物、份量、来源和置信度可见；用户能在一次修正内完成餐次、食物和宏量营养调整。
- 分享：从已确认记录生成 1080x1440（3:4）图片；系统分享面板可投递微信和小红书；图片不包含用户身份或未选择的健康数据。

## 用户流

```text
拍照/语音/文字
  -> 立即可见状态
  -> 结构化草稿（分项 + 份量 + 来源 + 置信度）
  -> 用户确认或修正
  -> 幂等写入 DietRecord + 图片引用
  -> 今日进度更新
  -> 可选生成图片卡并系统分享
```

## 产品原则

1. 模型负责识别候选，不负责裁决所有营养事实。
2. reviewed food table 只在名称匹配且份量可确定时覆盖模型估算。
3. “未识别/不确定”是正常状态，不能用 0 或虚构精确值掩盖。
4. 用户确认是写入边界；分享是另一次明确授权。
5. 性能只认相机返回后的真实端到端数据；成功分位数不得混入用户取景、取消或失败时长，也不以模型名或理论优化代替 p50/p95。

## 非目标

- 不承诺餐盘照片达到称重级精度。
- 不自动诊断代谢问题或生成处方。
- 不在本阶段接微信私有 SDK、自动发朋友圈或自动发布小红书。
- 不把睡眠和运动页面重构混入饮食 P0；它们在饮食闭环稳定后复用分享和状态机能力。

## 验收 Gate

- Backend 单元/接口测试覆盖清洗、份量解析、表值覆盖、fiber、所有者隔离和幂等。
- Mobile Jest 覆盖分项草稿、低置信提示、修正和分享入口；TypeScript 通过。
- iPhone 模拟器截图检查无溢出、遮挡、空白或低质感黑色输入区。
- 生产健康分通过，真实识别埋点开始产生 p50/p95 样本。
- 真机安装后微信与小红书分享面板能接收图片，用户确认分享卡内容和质感。
