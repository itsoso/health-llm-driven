# Pi 上线后的真实对话与任务完成能力复盘

日期：2026-09-13，时间均按北京时间。范围：只读分析，不包含代码修改、提交或发布。

## 判断

用户感受到的理解能力不足，有当前生产证据支持。官方 Pi 确实承担了工具循环，但原有的句式识别、权限语义判断、上下文组织和最终答案加工仍然决定模型能做什么。换循环没有自动改善这些部分。

当前最需要改变的是：让模型基于对话理解任务，由服务端校验明确的权限、数据范围与执行结果。现在不少地方仍要求服务端先用有限句式“理解整句话”，识别不了就拒绝模型提出的读取。多意图、口语扩写和纠错因此比单句查询脆弱。

上次发布修复了若干具体问题，是真实进展；但几个指定句式通过真实模型验证，不能证明整体对话能力提升。这次新样本已经暴露了验收覆盖的不足。下一轮不应继续把通过更多固定句式作为主要目标。

## 代码审阅：问题在哪里

### 1. Pi 负责循环，任务理解仍由旧控制逻辑主导

`backend/pi-runtime/index.mjs:150` 创建官方 `Agent`，使用 sequential 工具执行；`:162` 的模型请求通过 RPC 回 Python。`backend/app/services/pi_kernel.py:21` 是该循环的传输适配器。模型选择、提示词、工具效果与权限仍在 Python 一侧。

`backend/app/services/agent_kernel/intent_frame.py:12` 明确包裹已有 `classify_agent_utterance`。`context.py:58` 构建 snapshot 时先根据本轮文本生成 intent，再编译 goal；这里没有把完整会话任务状态交给语义理解器。已有 actionable references 能处理部分指代，不能据此说系统完全没有上下文，但也不足以支撑通用的多轮任务延续。

因此，目前证据更支持“旧任务控制方式的限制随迁移保留下来”，不能把能力提升寄托于替换循环本身。

### 2. 权限校验承担了过多自然语言理解职责

`backend/app/services/agent_kernel/capability_policy.py:2562` 对 Garmin 同步使用 `re.fullmatch`，只有规定句式且 `data == {}` 时允许。真实口语扩写无法匹配，尽管 intent 同样识别为 sync。

同文件 `:2707` 起在有限 daily plan 外重新推断单一查询维度与日历范围；`:2730` 返回 `health_query_calendar_window_unsupported`。`daily_read_plan.py:30` 的单问句匹配和今天总结规则修复了指定表达，却没有形成可组合的通用任务计划。

权限检查当然必须留在模型外：账户、租户、数据可见性、时间上限、写入授权、取消与幂等都是硬约束。问题是把“没有匹配句式”当作“无权读取”的充分理由。替换建议也不能走向让模型一句“用户授权了”就获得权限。

### 3. 可修复的语义失败与不可越过的权限失败混在一起

`backend/app/services/agent_policy_retry.py:5` 把语义未识别、日期范围未识别，与非本人查询和用户取消一起列为 terminal notices。`agent_executor.py:17142` 在当前工具批次结束后获取该通知，再以 terminate 结束 Pi 循环。

因此，对有明确自然语言日期的复杂读取，模型可能刚尝试完工具就失去修复机会。并非所有拒绝都会立即终止：例如同步句式拒绝和疾病实体澄清不在此终止表，实际仍可能有后续模型轮次，但后续轮次也不保证能取得新信息。需要按失败类型决定恢复方法，不能简单增加 max turns。

### 4. 同一请求在不同层被解释成不同任务

`utterance_intent_lexicon.py:291` 把“制定”放入计划创建词。`agent_kernel/goal_spec.py:263` 的通用目标回退沿用 intent。另一方面，`agent_executor.py:10279` 的开场确认已经显式区分“起草计划”与“持久化计划”，所以用户可能先看到“给出方案”，最后却得到“记录未完成”。

问题应在共享任务契约解决，而不是再给最终错误文案补一个“制定计划”的特例。方案生成、用户选定方案、保存为计划、确认执行和记录已完成，应是不同状态。

### 5. 上下文的时间、状态与任务相关性不足

`agent_conversation_service.py:690` 虽按消息时间排序，但 `:705` 给模型的常规历史仅保留 role/content，没有逐条发生时间。长历史还受窗口截断影响。这是时间指代失真的机制风险；不能仅凭这一点证明某个具体“昨晚提到”没有其他历史来源。

`health_context_lite_service.py:727` 将 is_active 的补剂定义和今日服用情况压成清单；`:760` 对 active 药品输出“当前用药”。“清单启用”“今天已记录服用”“用户刚说近期未服用”“医生确认方案”应明确区分，未打卡也不能推出未服用。当前字符串投影没有充分表达这些事实的新鲜度和冲突关系。

`agent_executor.py:19347` 已有“单一记录请求简短确认、不要主动展开旧病史”的提示要求，但真实照片记录仍输出了额外建议。再加一句同义提示的收益有限，需要让取数范围和最终输出目标共同约束这种行为。

### 6. 安全加工和质量观测还不等于好回答

`guidance_validator.py:355` 起按句扫描，`:381` 用固定占位替换被拦句子，然后直接拼接原文。它不是 Markdown 结构编辑器，也不是完整医学验证器。生产里的残缺表格和重复占位与此机制相符。

应保留不支持的主张不可发布这条底线，同时将可保留事实、被拦原因和需要补充的信息交给受约束的答复生成/确定性模板，输出完整短答，再做最终校验。不能直接删掉校验器让长文原样通过。

另外，照片路径的已验证回执计入 `turn_outcome`，但本轮 `kernel_trace.verified_receipts` 为零；计划失败时某些 kernel status 仍为 complete，而外层 run 已是 failed。这不是证明发生了假写入，而是不同状态字段职责不清，排障不能混用。

## 建议的改进顺序

以下是待实施方案和验收条件，不是已交付功能。

### 第一步：建立用户任务的质量基线

保留当前 Pi 和模型配置，先冻结一组脱敏、合成数据重建的真实多轮任务：查昨晚→同步→再查；记录→按比例修改→查回；分析昨天→今天方案→选择→保存；知识问题→结合自身观察→更正状态。将导致本次发现的例子放入开发回归，另留同义表达、顺序变化和未见过的多轮组合用于盲测。

评估必须经过实际入口、任务理解、Pi 工具循环、PostgreSQL 读取/隔离、证据输出和最终状态；写操作在隔离测试账户和数据库中执行。评审任务应采用独立的期望目标与 DB readback，不能用系统自身的 complete 证明自己完成。

已有 `backend/eval/runner.py:335` 的 health_agent_core 是不调用 LLM 的契约清单；`:180` 的 orchestrator 测的是合成环节。继续保留这些测试，但不能把它们当作完整 Agent 的任务成功率。

建议发布底线：固定关键旅程全部完成；同义/组合留出集达到预先设定的目标完成率，建议初始目标 95%；跨账户、引用越权、取消后写入、重复写入等安全负例零绕过。95% 是提议的门槛，当前尚无测量结果。每个基线同时记录目标完成、用户补充轮数、错误澄清、耗时、成本和不支持主张；不靠延迟或单一分数决定放行。

### 第二步：统一任务理解，保留服务端硬边界

让一个语义步骤根据当前输入、必要历史和尚未完成的任务提出结构化计划，至少分清：读取范围、多个子目标、生成答案、起草方案、建议保存、已授权写入、用户反馈、需要补充的具体槽位。

服务端固定本人身份、时区、数据权限、最大时间范围、工具参数类型、写入确认和幂等。语义计划是待校验输入，不能自行扩大授权；对来源材料中的指令、被引用的取消语句、第三方对象等继续保留安全测试。只对明确的本人只读请求提供可组合的域与时间能力；歧义写入必须澄清。

先以只读影子计划对照生产已记录轨迹，检查模型计划是否更贴近任务且不扩大权限；再替换查询路径，之后才处理有副作用的计划保存。不要同时改变内核、模型、权限和所有提示词，否则无法定位收益或回归。

### 第三步：把恢复过程接通

工具错误返回结构化的失败类型、已经确认的参数、缺少的字段及是否可重试：

- 明确跨账户、用户取消、无授权写入：硬拒绝或要求授权，不允许自动重试绕过。
- 类型/参数问题、已表达但未归一化的时间：在原授权范围内允许一次有信息增量的修复；相同参数不能重复调用。
- 数据未就绪：读取同步任务进度，等待预算内有结果则继续读取；未完成则保留任务并明确状态，避免要求用户重新说全部需求。
- 需要用户消歧：只问缺少的一项，保存已有范围。安全相关 ASR 日期或药名不能直接猜定。
- 用户表达不满或纠错：先识别上一任务哪里失败，说明具体问题，修正/继续该任务；不自动追加无关健康工具。

同步工具应输出可追踪 job_id，后续查询关联任务状态和目标日期的数据完整度。必须区别 queued、running、finished、目标数据可用，以及单次任务的部分失败。当前“同步时间有更新”不能代替这一完整协议。

### 第四步：让上下文和最终回答服务于当前任务

对历史消息和健康事实保留来源、发生时间、最近确认时间及适用状态；新陈述先作为本轮事实/冲突保留，不能未经授权把“近期没吃”改写成正式停药或删除方案。任务需要哪些数据再读取哪些，避免每次记录都激活全量健康建议。

纯记录请求采用回执驱动的短答；分析请求分清已记录事实、缺失项、推断和建议；出现真正安全告警可以补充必要信息。知识主张需要实际可定位来源，机构名和统一前缀不能替代逐项关联。医疗高风险结论缺证据时先给清楚边界和必要下一步，避免生成长方案再大面积挖空。

方案生成与执行状态关联现有 HealthAgendaItem、WriteIntent、ExecutionEvent；对话任务状态只负责衔接，不能另建一套与产品对象不一致的健康计划。

### 第五步：用受控比较决定是否继续改内核或模型

在同一模型、同一输入/历史、同一数据快照下，比较当前 Pi 路径与“Pi + 简化任务控制”的结果；硬安全边界完全相同，影子计划不产生生产副作用。只有这样才能判断是模型不具备能力，还是外围控制阻碍了它。

当任务完成率达到质量底线后，再做模型/上下文/生成长度优化。最新知识问答的模型首字约 49.33 秒、总时长 69.31 秒，另一轮模型首字约 52.17 秒、总时长 84.75 秒，足以说明这些个案生成有效答案的等待明显。这些是 perf 的模型首字指标，不代表用户在此之前看不到开场确认。没有匹配基线就不把延迟归因于 Pi 传输，也不直接把全部任务切到更快模型。

每次只灰度一个任务类型，用真实任务结果与负例回归决定扩大或回退。健康检查绿、离线契约绿、文本流结束，都不能替代这一层验收。
