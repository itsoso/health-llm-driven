# Reva 实际问答质量分析

分析日期：2026-09-12，北京时间。范围：当前用户最近三天的实际请求、对应回答、执行状态及脱敏事件证据。本文不包含健康原始数据、账户标识或鉴权信息。

## 结论与证据边界

Pi 替换了执行循环，但自然语言分类、工具权限判断、模型路由和终止回答仍使用多套既有判断。当前退化不能仅归因于模型能力，也不能靠继续补单句正则解决：同一意图通过不同工具得到不同判定，明确请求被模板澄清中断。

本次数据库只读采样覆盖 2026-09-10 08:41 至 2026-09-12 22:22 的 31 次请求：16 次运行失败、12 次运行成功、3 次等待用户确认。后三次是照片记录的正常确认流程。该样本属于一个账户且跨越多个版本，不能作为全站失败率，也不能将所有历史失败都归因于最新版本。运行成功也不代表回答质量完全合格。

对现行生产代码另做了纯函数探针；未调用模型、未执行健康数据工具、未写入健康记录。下表分别说明历史观察与当前复现。

| 今日我吃了啥 | 最新修复后仍一次失败、一次成功 | 事件分别为 health_manage 的 dimension_conflict 和 health_query 的日历查询放行。现行代码用相同输入与等价读取参数能复现。两个读取入口应消费同一个规范化查询范围。 |

| 给我今天总结 给我建议 | 再次要求提供类别和日期 | 修复后的真实请求仍失败。今日总结应有明确的产品默认范围和数据缺失说明；不应让用户自行列举内部记录类型。 |

| 修改晚餐食用比例 | 历史上输入 1/2 或二分之一仍提示使用 1/2 | 这两句现行解析已通过，不能继续报告为当前必现；但“晚餐我吃了1/2，请修改记录”仍解析失败。比例是否合法、对应哪条记录、以整盘还是个人份量为基准，应分别判定、分别澄清。 |

另外，睡眠与血氧的复合查询存在一部分工具被拦、一部分成功的情况。回答承认缺失血氧数据是正确的，但单一 succeeded 状态不能表达两个子目标的完成情况。部分正常饮食查询同时给出卡片、重复表格和重复总结，增加阅读负担。

## 代码原因

- `backend/app/services/agent_kernel/intent_frame.py::build_intent_frame` 仍包装原有分类器，Pi 迁移没有自动替换语义判断。
- `backend/app/services/agent_kernel/capability_policy.py::_calendar_question_dimension` 使用闭合整句匹配，仅允许特定后缀；一般的查询加建议不能匹配。
- 同文件 `project_diet_manage_list_to_turn` 接受的 operation 为 read/analyze，而“今日我吃了啥”的当前分类为 ask；其独立词表也不包含“啥”。它与 health_query 的解析已产生漂移，随后被判为 dimension_conflict。
- `backend/app/services/agent_kernel/health_semantics.py::resolve_health_read_act` 按文本子句更新查询授权状态；被分析文本中的否定措辞能改变当前请求的取消状态。
- `backend/app/services/agent_executor.py::_parse_explicit_diet_correction`、`_meal_fraction_utterance_has_factual_shape` 和 `_normalize_explicit_diet_update_tool_calls` 使用严格句式；多种无法解析情形最终汇总为 invalid_fraction，错误原因缺乏区分。
- 同文件 `_is_fast_eligible_turn` 依赖分类器；高风险质量地板在主流程中还受 staged 模式条件控制。风险判定需要在快速路由前统一生效，不能仅依赖“建议”一词是否出现。
- 同文件 `_completion_status_from_finish_reason` 将 stop 映射为 complete，而策略终止文本也设置 stop。本样本 16 次失败中，11 次回答元数据为 complete。这是“生成结束”和“用户目标完成”两个语义混用，不能据此断言所有客户端都显示成功。

## 改进顺序与验收

### P0：统一理解结果，保留真正的权限约束

一次解析得到对象、领域、时间范围、操作和子目标，供分类、工具参数归一化及回答共同使用。认证用户身份始终由服务端绑定，不能由模型指定；写入仍需明确授权、准确目标、幂等与回执。模型输出的语义计划只是待校验输入，不直接成为权限。

读取与写入采用不同的恢复方式。对于已认证用户明确提出的自身健康查询，在既定产品范围内允许补全默认日期或汇总范围。读取语义尚不充分时，只问缺失部分；不把未知输入放宽成任意数据查询。写入目标或份量基准不明确时，保留只读查找及精确澄清，不猜测执行。

验收至少覆盖同一请求的 health_query / health_manage 等价路径，以及“啥/什么”“今日/今天”“查询后给建议”的改写。等价读取不能因模型工具选择而随机失败。

### P0：统一完成状态与失败恢复

区分已完成、部分完成、待确认、执行失败与状态待核对。每个子目标绑定所需证据；回答文本、运行状态与客户端展示消费同一结果。同步、查询、写入分别以同步结果、读取结果和写入回执证明完成。

取消指令只作用于用户当前要求的动作。引用、粘贴材料及工具返回内容不会自行取消或授权任务。比例、目标、日期等错误分别返回可操作原因，禁止让用户反复提交已经符合格式的内容。

### P1：提高回答质量与模型路由一致性

风险判断先于速度优化。普通记录与明确读取可以走快模型；个性化干预建议需要相应证据和质量门槛。已有用户画像可以作为上下文，但不能冒充本轮查询结果，也不能把单餐写入回执外推为全天统计。

日总结只展示已查到的事实、重要变化、少量可执行建议和缺失项。卡片负责结构化事实，正文负责解释，避免重复整张表。时间范围、单位和汇总值由工具结果携带并统一渲染。

### P1：用实际任务轨迹补齐验收

保留现有权限与隔离测试，再加入脱敏实际失败场景的完整 AgentExecutor/Pi 回放，覆盖工具选择、拒绝后的恢复、重复请求、追问和最终回答。写路径使用隔离测试账户与 PostgreSQL，不向真实健康记录写入测试数据。

必须区分不同评测的证明范围：`backend/eval/runner.py::_run_orchestrator_case` 验证合成环节；`_run_health_agent_core_case` 明确是尚未调用 LLM 的离线用例契约。它们各有用途，但通过不能证明完整用户任务成功。上线前应同时具备语义改写测试、工具路径一致性测试和真实模型完整链路结果。
