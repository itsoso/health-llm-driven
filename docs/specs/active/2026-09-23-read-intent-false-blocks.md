# 明确读取和既有饮食修正的语义修复

Status: implementing · Owner: Codex · Updated: 2026-09-23

## 决策与准入

classification: bugfix。承接 PRD R3/R5/R9/R10，恢复明确本人查询及用户确认的
饮食修正；source_of_truth 为认证用户的已有记录和服务端绑定的上下文。
对象：WriteIntent、HealthTwin、ExecutionEvent；surface：Backend → Mobile Chat。
安全边界为健康写入、隐私和医疗证据；不作处方、诊断或因果判断，写入仍需
明确用户指令和既有确认/目标校验。不新增用户输入负担、数据表或后台同步。

## 最小流程与契约

1. 分析请求中的“给出你的建议”属于回答目标，不是查询条件。最近一周应绑定
   到用户时区的明确日期；未消费完的限制、其他人的记录不能被丢弃。
2. “睡眠血氧”必须携带实际血氧来源、窗口、质量和缺失边界，不得用仅睡眠
   时长/评分的结果冒充。本次仅读取本人范围内的血氧日汇总，复用既有来源
   排除规则；日汇总不能证明夜间覆盖、ODI 或诊断。不调用会回退到最近一夜的
   读取器。无法安全绑定时明确说明尚未查询，不归咎于用户未写明日期。
3. 基于已识别餐食修改今天午餐，识别为修改目标。仅通过既有服务端授权的
   前置查找定位本人、日期、餐别；没有唯一记录或没有可信餐食来源时澄清，
   不从模型参数/任意历史文本捏造目标、食物或营养，也不新增一条替代更新。
4. 回合被拦截/失败时，不额外附加容易被误解为个人结论的系统知识卡。
   成功回合仍保留知识依据；真正的安全警报和已核实保存回执不受影响。

无新外部 API/客户端类型或迁移；如调查发现必须扩大数据契约，先更新此 spec。
不回填生产记录、不更改安全阈值、不纳入不可信血氧源、不将缺失值当正常。

## 验收与验证

- 截图原话及正常同义表达正例；引用、否定、假设、第三方、超范围参数反例。
- 修改目标及可信来源缺失时只澄清，跨用户/跨餐记录不变。
- 查询范围和读取结果一致；真实 Pi 流的阻断回合不发出/持久化补充知识卡，
  正常完整回答仍发卡，SafetyGuardian 警报仍可见。
- 聚焦 pytest、CI-mode 集成、LLM change gate、独立安全复审；若改 DB 读取
  语义追加 PostgreSQL 证据。上线另须明确授权、全绿精确 CI 和受控部署。

回滚沿用上一已验证后端 revision；本轮不处理旧发布锁，不声称 OTA 已发布。

## 续作：照片修正的最小确认流程

准入：bugfix / WriteIntent + HealthTwin + ExecutionEvent，Backend 真源，Mobile
主执行面，manual_confirm；不新增自动写权限、API 或数据库列。
目标是消除重复手填，同时不让模型或历史自由文本决定更新目标。

结构化餐食识别成功后，将食物描述和实际食用比例的服务端签名快照保存在
所属用户图片消息的 metadata，最长引用 24 小时。快照与用户、会话、消息、
图片集合绑定；不以普通模型回答作为识别来源。
明确的“基于识别的这一餐来修改今天午餐记录”只引用紧邻的图片回合，
只读取本人当前日期/指定餐别，要求唯一记录。缺失、过期、冲突、跨会话或
已经另存成另一餐时给出具体说明，不查询其他日期，不新建/覆盖任何饮食。

返回已有 record_quality 修正表单，原食物/营养/版本保留为 baseline，
新增可选 `adjust_record.proposed_food_items` 只预填输入。
Mobile 用户确认后走现有原子营养重算 API（版本比较 + 幂等），失败不回退
普通 PUT、不称已保存。旧客户端可按回复中的描述手动填写现有编辑页。
现有餐食照片不转移；本次替换的是用户确认的食物描述和重算后的营养。
一轮多餐选择、跨回合搜索、未落快照的历史照片及照片资产迁移不在首片范围。

验收：正向照片→原话→预填→确认重算；无确认不写；否定/第三方/引用不启动；
快照篡改/来源失效/目标多条拒绝；PG 读写与 Mobile 真实组件回归。
