# 饮食修正与聚餐个人份额

Status: implementing · Owner: Codex · Updated: 2026-09-21

## 决策与准入

针对 Mobile 聊天饮食卡及饮食详情，修正食物描述时明确重新估算，聚餐时单独确认个人所吃比例。承接 PRD R5/R10/R11 的手工录入能力，不增加一级入口。

- first_class_objects: HealthTwin（DietRecord 投影）、WriteIntent（用户确认的原记录修正）、ExecutionEvent（复用现有写入通知）。
- core_loop_step: capture → correction → review；source_of_truth: authenticated DietRecord。
- safety_level: 健康事实写入；autonomy_tier: manual_confirm；不作处方或因果判断。
- evidence: 用户食物描述、显式个人比例、估算营养；保持“估算”标识。
- success_metric: 改文字后五营养一起重算；整桌 1/5 仅计入个人 20%；重复修正不连乘。
- 新增负担仅为可选份额选择；不根据就餐人数自动推断本人份额。
- 不做逐菜自动分配、酒精比例重算、营养精确性承诺、新 DB 表或原生能力。

## 用户流程与表面契约

Mobile 保留完整食物描述，提供“我吃的份额”整份、1/2、1/3、1/4、1/5、自定义分数/百分比；提示聚餐填整桌菜，并按各菜均匀取食估算，不均匀时应改具体菜量。描述变化显示“保存时重新估算”，旧数值不冒充新结果；此时禁用手动营养输入。只修改手动营养继续 PUT。描述/份额修正经 POST 成功后才替换卡片及汇总；失败保留输入且不宣称保存成功。

Backend 复用原子 recalculate-nutrition，增加可选 consumed_fraction（0 < 值 <= 1），幂等摘要包含份额。描述无 canonical 比例后缀；服务端按整桌基准确定性缩放。仅比例变化复用已有有效营养基准，不重复调用模型或叠乘。比例信息沿用（按实际食用1/5计）格式，客户端再次打开拆出完整描述与比例；整份移除后缀。旧客户端省略字段仍兼容。无 schema migration。

带份额的既有基准必须通过服务端 HMAC 校验，签名绑定 owner、record、整桌描述、比例及五项已保存营养；客户端可写 raw JSON 或文字不能作为证明。旧记录缺少签名或手动修正使签名失效时，重新估算整桌再按新份额计算。文字同时包含自然语言食用/剩余比例时，在模型和快速路径前拒绝，返回 `diet_portion_description_ambiguous`；Mobile 保留输入并提示把整桌描述与个人份额分开，不静默重复折算。

## 安全与 AI 边界

结构化份额编辑中，食物描述内的裸比例、百分比、分配语句均要求移入个人份额；明确物理菜量（如半碗、1/2 碗）仍可填写。烹饪状态（如半熟、五成熟）不视为份额。只读营养显示最多两位小数，但保留原始保存精度。

所有读写按认证 owner 隔离；expected_updated_at + 行锁 CAS + Idempotency-Key 保留。冲突要求刷新，不盲重试。份额输入拒绝空、0、负、超过 100%、非数；未明确个人份额、假设和单菜比例不得自动缩放全桌。模型仅估算食物，份额由确定性代码应用；含酒路径维持拒绝重算。健康载荷不进入日志。

## 验收

1. 改食物文字：明确重算状态、禁用旧营养编辑、五项结果原子刷新，失败可重试。
2. 全桌 1000 kcal，选 1/5 → 200；改 1/3 再 1/5 → 200；每次按整桌基准而非当前值连乘。
3. 自定义 20% 与 1/5 等价；非法输入不能保存。
4. 重开已缩放记录还原份额；改描述后继续保持份额且只缩放一次。
5. “我只吃了1/5”“聚餐，我只吃了1/5”附图事实可识别；假设、他人份额、单菜份额不误缩放。
6. CAS、owner、幂等、酒精与估算失败测试；PostgreSQL 并发；Mobile 组件/屏幕回归与类型检查；CI-mode 闸门、独立安全评审通过后发布。
